# MAAS #2146166 — Intel AMT power driver broken

Findings and a proposed fix.

- Bug: <https://bugs.launchpad.net/maas/+bug/2146166> ("Intel AMT power driver broken", High, Triaged)
- Related: <https://bugs.launchpad.net/maas/+bug/2107706> ("Power error for intel AMT when using HTTPS: Unsupported protocol")
- Suspected regression: `c7da3d3ad20af23dd883924633c761e2322e0e62`

**TL;DR:** the two bugs are the same commit seen from opposite sides. `--endpoint` was
introduced to enable HTTPS, but `--endpoint` silently discards `--username`/`--password`
and is fragile to URL metacharacters. It is also **not needed** — `--cacert` already
selects the https scheme. Dropping `--endpoint` fixes both bugs.

**even better TL;DR**: Reproduction and suggestion for fixes at the end of this file.

Tested with `wsmancli 2.6.1` (Ubuntu 24.04) against Intel AMT 12.0.96.2562.

---

## Finding 1 — `--endpoint` and `--username`/`--password` are mutually exclusive

`wsmancli/src/wsman.c` (~line 783):

```c
if (endpoint) {
        cl = wsmc_create_from_uri(endpoint);        // username/password IGNORED
} else {
        cl = wsmc_create(server,
                        server_port,
                        url_path,
                        (cainfo || use_https) ? "https" : "http",
                        username,
                        password);
}

if (non_interactive == 0) {
        wsmc_transport_set_auth_request_func(cl, &request_usr_pwd);
}
```

When `--endpoint` is set, credentials **must** be embedded in the URL; `-u`/`-p` are never
read. If the URL doesn't yield them, the client has no credentials and falls through to
`request_usr_pwd()` — which is the reported symptom:

> `Failed to query node's BMC - Unable to extract AMT version from amttool output: User name: Password:`

## Finding 2 — credentials in the URL are not escaped

MAAS builds the endpoint by string interpolation:

```python
f"{'https' if port == '16993' else 'http'}://{power_user}:{power_pass}@{ip_address}:{port}"
```

The password is not URL-encoded. Reproduced against `wsman identify`:

| password | result |
|---|---|
| `plain` | connects |
| `a@b` | connects |
| `a@@b` | **`URL rejected: Bad hostname`** (curl error 3) |
| `S3cr@@t!` | **`URL rejected: Bad hostname`** (curl error 3) |

curl's URL parser tolerates a single stray `@` in the userinfo but rejects a doubled one.
Percent-encoding fixes it (`S3cr%40%40t!`), but see Finding 3 — that isn't the fix we want.

This matters because AMT **enforces** a strong password containing a special character, so
`@` in AMT passwords is common in the field.

## Finding 3 — `--cacert` is what actually selects https

From the same ternary above:

```c
(cainfo || use_https) ? "https" : "http"
```

There are exactly **two** ways to get the https scheme in the whole codebase:

- `cainfo` — set by `-c` / `--cacert`
- `use_https` — set by `--https`

`--https` exists in wsmancli master but is **not present in Ubuntu 24.04's 2.6.1**.
The config file (`-C`) can only set `agent`, `port` and `authentication_method` — no help there.

So on current Ubuntu, **`--cacert` is the portable https switch**, and `--endpoint` is
unnecessary. Verified:

```console
$ wsman identify --hostname dell1.lan --port 16993 \
    --username admin --password "$(cat ~/amt_pass)" -y digest \
    --cacert /etc/ssl/certs/ca-certificates.crt -d 6

* Connected to dell1.lan (192.168.15.11) port 16993
* SSL connection using TLSv1.2 / ECDHE-RSA-AES256-GCM-SHA384
* subjectAltName: host "dell1.lan" matched cert's "dell1.lan"
* SSL certificate verify ok.
```

Password passed via `argv` — no URL, no encoding hazard.

Notes:

- Pointing `--cacert` at the **system bundle** (`/etc/ssl/certs/ca-certificates.crt`)
  works for publicly-trusted AMT certificates *and* for private CAs, because
  `update-ca-certificates` regenerates that bundle to include locally-installed roots.
  It changes nothing about verification — curl's `CAINFO` defaults to that same file — it
  just trips the scheme selector.
- If you want https *without* verification, `-c <any file> --noverifypeer --noverifyhost`
  works, since `cainfo` only needs to be non-NULL.

## Finding 4 — separate defect: OpenSSL 3 refuses AMT ≤ 12 regardless

Independent of anything MAAS does. AMT 12's TLS stack does not advertise RFC 5746 secure
renegotiation, so OpenSSL 3 (Ubuntu 24.04) aborts the handshake:

```
error:0A000152:SSL routines:final_renegotiate:unsafe legacy renegotiation disabled
```

Surfaces via curl/wsman as `Unsupported protocol` / `Received HTTP/0.9 when not allowed`
— i.e. bug #2107706's headline error. It is **not** a certificate problem and is not fixed
by anything in Findings 1–3. Workaround:

```ini
# OPENSSL_CONF
openssl_conf = openssl_init
[openssl_init]
ssl_conf = ssl_sect
[ssl_sect]
system_default = system_default_sect
[system_default_sect]
Options = UnsafeLegacyRenegotiation
CipherString = DEFAULT@SECLEVEL=0
```

MAAS will need a decision here: ship this shim for the `wsman` subprocess, or document
that HTTPS AMT requires it. Fixing the URL handling alone will not make HTTPS work on
AMT 12 hardware.

## Finding 5 — snap confinement (unverified, flagging only)

MAAS installed as a snap has its own confined filesystem, so a root CA installed on the
host with `update-ca-certificates` may not be visible to the `wsman` the snap invokes.
This argues for an **explicit, configurable CA path** in the power driver rather than
relying on the default system bundle. I have not tested this — worth confirming.

## Proposed fix

Drop `--endpoint` entirely. Revert to the discrete options and use `--cacert` to select
the scheme.

```python
command_args = (
    "--hostname", ip_address,
    "--port", port,
    "--username", power_user,
    "--password", power_pass,
    "-y", "digest",
)
if port == AMT_HTTPS_PORT:
    # In wsmancli, the scheme is chosen by:  (cainfo || use_https) ? "https" : "http"
    # --https is not available in Ubuntu 24.04's wsmancli 2.6.1, so --cacert is the
    # portable switch. Defaults to the system trust store; override for private CAs.
    command_args += ("--cacert", ca_bundle or "/etc/ssl/certs/ca-certificates.crt")
```

Why this is better than percent-encoding the endpoint URL:

- **No URL at all**, so no encoding hazard for any password character
- Works on wsmancli 2.6.1 (Ubuntu 24.04), not just master
- One code path for private CAs and public CAs
- Restores the pre-3.6 behaviour that users report working, *without* re-breaking HTTPS

> ⚠️ A naive revert to the old syntax **without** `--cacert` would fix #2146166 and
> re-break #2107706, because `-h`/`-P`/`-u`/`-p` alone always speak plaintext HTTP.
> Anyone "cleaning up" the seemingly-redundant `--cacert` later would silently drop all
> HTTPS users back to port-16992 plaintext. Worth a comment in the code.

When wsmancli ≥ 2.7 is widely available, `--https` becomes the more honest flag and
`--cacert` can go back to meaning only "verify against this".

## Reproduction

```bash
# Fails: prompts for credentials / rejects the URL
wsman identify --endpoint "http://admin:$(cat ~/amt_pass)@192.168.15.11:16992" \
  -V -v -d 6 -y digest --noverifypeer --noverifyhost

# Works over HTTP
wsman identify --hostname 192.168.15.11 --port 16992 \
  --username admin --password "$(cat ~/amt_pass)" -y digest -d 6

# Works over HTTPS (this is the proposed fix)
wsman identify --hostname dell1.lan --port 16993 \
  --username admin --password "$(cat ~/amt_pass)" -y digest \
  --cacert /etc/ssl/certs/ca-certificates.crt -d 6

# In case the above fails you can try a custom OpenSSL conf
cat > /tmp/openssl-amt.cnf <<'EOF'
openssl_conf = openssl_init
[openssl_init]
ssl_conf = ssl_sect
[ssl_sect]
system_default = system_default_sect
[system_default_sect]
Options = UnsafeLegacyRenegotiation
CipherString = DEFAULT@SECLEVEL=0
EOF
OPENSSL_CONF=/tmp/openssl-amt.cnf wsman identify --hostname 192.168.15.11 --port 16993 \
  --username admin --password "$(cat ~/amt_pass)" -y digest \
  --cacert /etc/ssl/certs/ca-certificates.crt -d 6

# with process substitution so no file on disk is needed (needs e.g. BASH)
amt_conf() {
  sed 's|^providers = provider_sect|&\nssl_conf = ssl_sect|' /etc/ssl/openssl.cnf
  printf '\n[ssl_sect]\nsystem_default = amt_sect\n\n[amt_sect]\nOptions = UnsafeLegacyRenegotiation\nCipherString = DEFAULT@SECLEVEL=0\n'
}

amtwsman() {
  OPENSSL_CONF=<(amt_conf) wsman "$@"
}

```

On AMT ≤ 12, prefix the HTTPS calls with `OPENSSL_CONF=/path/to/legacy.cnf` (Finding 4).

Getting a browser-valid certificate onto the AMT devices in the first place is covered in
[README.md](README.md) — notably, MeshCommander cannot issue one, because it never emits a
`subjectAltName`.
